# 原厂采集、数值发布与屏幕节奏

分析日期：2026-10-24。依据为私有主控备份，SHA-256 见 [机器对照结果](cadence-stock-verification.json)。以下结论来自原厂 ARM 指令与模拟执行，不来自产品文章；未测量实机波形。

## 结论与改动

之前的运行时收到甲醛、PM 或温湿度采样便标记屏幕需要刷新，`0x01` 查询也直接使用最新 PM/温湿度结果，造成数值变化比原厂频繁。原厂将处理、数值快照和显示发送分开，没有在甲醛/PM 的这条路径上做通用移动平均。

| 工作 | 原厂行为 | 当前实现 |
| --- | --- | --- |
| 甲醛请求/温湿度处理 | 每 1000 tick 唤醒 | 正常采集约每秒；保留初始化和故障恢复 |
| PM 接收任务 | 每第三轮唤醒 | 每 3 秒安排一次接收；未完成窗口继续等待 |
| 正常显示与查询快照 | 每第三轮渲染并保存数值 | 每 3 秒更新四类数值及正常显示 RAM |
| 屏幕 RAM 发送 | 100 tick 定时器分频 | 首次周期发送约 2200 ms，之后每 2100 ms；另有冒号每 500 ms 刷新 |
| `0x01` 查询 | 数值读显示任务缓存，状态另读 | 快照内数值保持，健康字段实时更新 |
| `0x19` 查询 | 原始甲醛变量 | 返回最新原始值，不受 3 秒周期限制 |

主时钟 OSC8M 8 MHz、SysTick reload=7999，据静态配置推导 1 tick=1 ms。上述周期以任务/定时器建立时刻为基准，真实 RTOS 启动相位、调度延迟和晶振误差未实测。原厂渲染与发送异步，所以屏幕可见变化可能相隔 2.1 或 4.2 秒，不能把“3 秒渲染”理解为屏幕总在每第三秒变化。

当前实现把采集结果放在 `m1_runtime.measured`，正常数值快照放在 `state.sample`，屏幕缓存为 `display_ram`。迟到调度只处理当前值并推进周期，不补发一串过期样本。冒号相位、开关、亮度、调试和 I²C 重试可以额外触发传输，但不会提前发布正常采样或移动周期相位。真实 `0x10` 全段测试按原厂分支暂停正常快照；新增调试覆盖仍维持后台快照。

## 冒号每秒闪烁

v0.9.3 将时间冒号设为每秒一个完整周期：亮 500 ms、灭 500 ms。软件只修改 RAM[0]、RAM[3] 的 bit3；普通数值调试也显示当前相位，原始段覆盖与全段测试不受影响。时间设置成功后重新从亮相位计时；关屏仍推进相位但不为闪烁额外发送，重新开屏显示当前相位。延迟调度跳过过期相位，32 位毫秒回绕不重启周期。普通数值仍每 3 秒产生一次快照。

这是按用户观察需求增加的行为，不称为已完整复现原厂闪烁：备份时间渲染 `0x68b8` 在 `0x6954–0x6966` 将两点置亮，屏驱初始化 `0x64a4` 发送 `0x88` 关闭硬件全屏闪烁，尚未确认原厂每秒切换路径。没有使用会让全部 LED 一起闪的硬件模式；只增加显示传输，不加速传感器采集。

## 保留的数值处理

- 甲醛：最新原始整数直接保存。正常渲染时原始值小于 11，首次低值显示/返回 0，此后为 10；高于 9999 时保留前次查询值，屏幕显示上限段形。低值锁存只在正常渲染时推进。
- PM 模式 3：一次接收完整 64 字节，在偏移 0–31 搜索第一个有效 32 字节候选，默认按此模式启动。前两个完整窗口用于预热，即使窗口损坏也计次。前值 ≤149、当前值 ≥1001 时拦截一次突升，下一窗口确认；不是对两帧求平均。偏移 32 的完整第二帧不在原厂搜索范围内。
- PM 模式 2：每 3 秒发 `42 4d e2 00 00 01 71` 并接收对齐 32 字节，前四个校验有效的回调用于预热；无模式 3 的突升拦截。
- 温湿度：保留已有四状态定点补偿，约每秒推进，显示有效开关参与补偿；没有再加额外平均层。

PM 不再应用其他串口的 100 ms 字节间隔丢弃规则：模式 3 的两段数据可能相隔约 1 秒，过早清缓冲会使 64 字节窗口无法完成。接收完成后等待下一次任务安排，期间不不断发布串口中的后续帧。原厂重叠坏候选间的校验累加器残留未复制，当前每个候选独立验算。

自动 PM 探测的 10 秒重试、三次坏帧/6 秒失效和 SHT 限流软复位仍是先前新增的恢复策略，不因本次周期对照而称作原厂已确认实现。

## 验证与复现

`tests/test_runtime.c` 覆盖毫秒级持续变化输入、32 位计时回绕、查询缓存/原始查询、正常/调试显示、I²C 失败不冻结快照、64 字节跨调度保留、两种预热、偏移 31/32 边界以及 ACK 误识别。

`tools/verify_cadence_stock.py` 执行原厂调度任务和定时回调，记录实际唤醒/发送次序；再将每毫秒改变的输入分别送入原厂渲染函数及当前 C 运行时，比较 13,001 次四类数值快照及 32 次屏幕写入的 928 字节。原厂周期发送时刻全部保留，新增每 500 ms 的冒号发送；将原厂缓存仅按当前冒号相位修改后，逐字节比较完整输出。结果见 [cadence-stock-verification.json](cadence-stock-verification.json)。

```sh
build/analysis-venv/bin/python tools/verify_cadence_stock.py /path/to/private-backup.bin
```

工具只接受指定哈希，原厂代码在模拟 Flash/SRAM 中执行，RTOS、I²C 等辅助调用使用替身，不操作设备。私有原厂镜像不进入公开仓库或 CI。主机测试、原厂指令对照与 ARM 构建不能替代真实传感器采样、屏幕观感及新镜像启动验收。
